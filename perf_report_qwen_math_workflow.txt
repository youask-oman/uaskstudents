Why it takes >2 minutes (root causes)
--------------------------------------
1) Bottleneck decomposition (with proof)
- Bottleneck #1: `freeform_attempt_generate_call` consumed 1028838.9 ms total across 8 runs (99.63% of end-to-end time). This is the dominant sink in both cold and warm runs.
- Bottleneck #2: strict 3-attempt loop always runs. Evidence: every run had `attempt_count=3` in telemetry; none of the 8 runs produced a validation pass (`validated=false` each run).
- Bottleneck #3: timeout retries add huge penalty on warm runs. Evidence: 2 timed-out attempts with avg 120138.4 ms (total 240276.8 ms). A warm runs with timeout reached ~202s total.
- Bottleneck #4: UI streaming is effectively delayed until generation is complete. Evidence: first SSE byte arrives fast (~353.6 ms avg), but first delta arrives at ~129048.9 ms avg, and done follows only ~28.2 ms later.
- Non-bottlenecks: DB work is tiny (all `db_*` labels combined 331.1 ms, 0.032% of total). Prompt/tier resolution + billing prework together are ~270.5 ms total (0.026%).

2) Classification: where delay comes from
- Compute bound (model inference/generation): dominant (~99.63% via freeform generation calls).
- I/O bound (DB/filesystem/network setup): very small for DB (~0.032%); DNS/TCP probes are milliseconds.
- Queueing bound: none observed in this route (no worker queue dispatch in traced path; endpoint runs inline).
- Application bound: retry policy + strict validation gate + delayed delta emission amplify user-visible latency.

Where we should make changes (recommended fixes)
------------------------------------------------
High impact / low risk
1) File: backend/app/api.py (freeform loop in `solve_v3_stream_endpoint._inner_generate`)
   Change: reduce default attempts from 3 to 1 for interactive chat (or make attempt 2/3 conditional on explicit user retry).
   Why: all runs already return attempt #3 after long waits; cutting retries removes 30-120s+ from p95.
   Monitor: `attempt_count`, `total_ms`, `freeform_attempt_error` rate.
2) File: backend/app/api.py + backend/app/services/solve/freeform_solver.py
   Change: stream attempt output to SSE immediately (emit `delta` as chunks or emit attempt-1 result without waiting for attempt-2/3).
   Why: current first visible token is delayed until completion; first-byte is fast but first-delta is late.
   Monitor: `first_delta_ms`, `done_ms - first_delta_ms`, user abandonment rate.
3) File: backend/app/services/solve/freeform_solver.py (`generate_freeform_solution`)
   Change: lower freeform timeout default (120s -> 45-60s) and handle timeout explicitly with clear fallback message.
   Why: 120s timeout attempts caused >2 minute warm outliers.
   Monitor: timeout count, solve success rate, p95 latency.
High impact / medium risk
4) Files: backend/app/services/solve/freeform_solver.py (`validate_freeform_output`) + backend/app/api.py (attempt-selection logic)
   Change: relax hard validation gate (treat rubric as quality score, not strict pass/fail) and stop retrying when answer extraction is present.
   Why: current rubric marks all 8 runs invalid, forcing full retry budget every time.
   Monitor: `validated` rate, attempt_count distribution, solution quality QA.
Medium impact / low risk
5) File: backend/app/services/solve/freeform_solver.py (prompt construction)
   Change: trim freeform prompt template/context where safe. Current prompt payload is ~2506 bytes / ~543 est tokens before generation.
   Why: smaller prompt can reduce generation latency modestly.
   Monitor: token/char input size vs latency correlation.
6) File: deployment config/env (`OLLAMA_KEEPALIVE`, optional startup prewarm)
   Change: keep model warm aggressively if resource budget allows.
   Why: cold penalty was not dominant in this sample, but prewarm can reduce variance.
   Monitor: first attempt latency distribution split by idle time.

Decision-ready summary
----------------------
If we do only one thing: change the freeform retry policy in `backend/app/api.py` to stop running 3 blocking attempts by default (attempts=1 for interactive flow) and emit the first attempt result immediately. This directly targets the measured 99%+ time sink and will collapse >2-minute tails.
